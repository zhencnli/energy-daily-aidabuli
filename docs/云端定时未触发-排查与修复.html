一、为什么今天没触发（诊断）

我已在本地核实：线上 feed 最新单集停在 10-06，git 历史里只有 1 次自动化提交（10-06 12:50，是手动 workflow_dispatch，不是 cron）。说明 schedule: 很可能从未自动触发过。

由于本机 gh 未登录、仓库为私有，我无法直接读 Actions 日志。但按现象，根因锁定在以下三种之一：

① 工作流被禁用（最常见）——GitHub 的 scheduled workflow 需要在 Actions 页面处于 Enabled 状态。若此前被关掉或从未激活，cron 就完全不跑。

② GitHub 调度延迟——免费额度共享 runner，schedule 经常延迟十几分钟到数小时，极少跳过。今天 06:37 / 07:25 的两次可能稍晚才到，但到 09:25 仍未出现，概率偏低。

③ 触发但失败——密钥失效 / 依赖安装 / LLM 接口 / COS 上传失败，会留下一条红色 run。失败不产出单集也不提交。

因为 site.yml（push 触发）此前能成功部署，说明 Actions 整体没被禁用，所以 ① 多半是该 workflow 单独的 Enable 状态问题，或 ③。

三、如何避免以后再漏

方法 A（推荐，零成本）：每天上午顺手看一眼官网或 feed，确认有新单集。最省事，但因为 GitHub schedule 本身不可靠，仍可能偶发漏跑。

方法 B（双保险，需 PAT）：在本机 Windows「任务计划程序」里，加一个每天 08:30 的任务，调用 GitHub API 触发 workflow_dispatch。这样即使 GitHub 的 schedule 不跑，本地也会兜底触发一次。需要一个有 workflow 权限的 Personal Access Token（PAT）。

方法 C：保持现有两个 cron 时间点（06:37 / 07:25），启用后基本够用，配合方法 A 监控即可。

四、常见坑

  • 60 天无活动自动禁用：GitHub 会在仓库连续 60 天无 push 后，自动禁用 scheduled workflow。本仓库新建不用担心，但长期要保持偶尔提交（你每天的 bot 提交本身就是活动，能保活）。
  • Fork 仓库默认不启用 schedule：如果你的仓库是从模板 fork 的，需要在 Settings → Actions 手动开启。
  • PAT 需 workflow 范围：若用方法 B，创建 token 时务必勾选 workflow 权限，否则无法 dispatch。
  • secret 过期：若步骤 3 跑出红色 run 且报 401/403，多半是 TENCENT_COS_SECRET_KEY 或 DEEPSEEK_API_KEY 失效，去 Settings → Secrets 更新。
